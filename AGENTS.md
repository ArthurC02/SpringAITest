# Repository Guidelines

Solution-wide guidance only. Each area has its own `AGENTS.md` (+ `CLAUDE.md` importing it) with layout, commands, and area-specific gotchas — **read the area file before working in that area**; Claude Code loads it on demand when files there are touched.

## Subagent Delegation

**Delegate by default — do not wait to be asked.** Route substantive work to the project subagents in `.claude/agents/` and run independent ones in parallel; the main agent orchestrates (write the spec, delegate, integrate results):

| Agent                  | Use for                                                                             |
| ---------------------- | ----------------------------------------------------------------------------------- |
| `dotnet-implementer`   | Any implementation in `platform/` or `backend/` (+ xUnit tests)                     |
| `frontend-implementer` | Any implementation in `frontend/`                                                   |
| `python-implementer`   | Any implementation in `workflow/` (nodes, engine, skill compiler, sandbox + pytest) |
| `code-reviewer`        | Review after every non-trivial change, before declaring done                        |
| `code-simplifier`      | Simplify/refine recently changed code (clarity, reuse, dead flexibility) — behavior-preserving, after review |
| `e2e-verifier`         | Full-chain verification via docker compose when cross-service behavior changed      |
| `docs-updater`         | Sync README/AGENTS/docs files after feature or architecture changes                 |

Only trivial work (typo-level edits, quick Q&A) stays in the main loop.

**Every subagent definition must pin all four knobs in its frontmatter:** `model`, `tools`, `hooks`, and MCP access (MCP tools are granted as `mcp__<server>__<tool>` entries inside `tools`). Where one is deliberately absent (e.g. no hooks for a docs-only agent), record that as a YAML comment in the frontmatter — omission must be a decision, never an oversight. New agents follow the same rule.

## Cross-Service Contracts

These facts span two or more areas — changing one side silently breaks the other, so they live here, not in the area files:

- **Public chat API** (platform): `POST /api/chat` (blocking), `POST /api/chat/stream` (SSE), `GET /api/chat/history`. POST bodies take `message` plus optional `userId` and `conversationId` (short-term grouping; blank falls back to `userId`). When logged in, identity, mem0 grouping, and persistence always derive from JWT `{tenant}:{user}` and ignore body `userId`; anonymous requests use the caller values only for short-term continuity, never mem0 or persistence. `GET /api/chat/history` is filtered by the caller's login identity — anonymous requests get an empty array, not a 401 (endpoint stays `AllowAnonymous`). The AG-UI copilot (below) shares authenticated persistence: its turns show up together with `/api/chat*` turns in `GET /api/chat/history`.
- **Two SSE formats, both deliberate:** `/api/chat/stream` writes hand-rolled `data:<value>` (no space); the AG-UI endpoint `/api/copilot/agui` writes protocol-standard `data: ` (with space). The frontend parses chat SSE with `fetch` + `ReadableStream` (`EventSource` cannot POST a body). Every proxy hop (Vite dev proxy, frontend nginx) must keep `proxy_buffering off` on SSE paths. **Streaming error frame:** if `/api/chat/stream` fails mid-transmission (after chunks have been sent), platform writes `event:error\ndata:<fixed Chinese message>\n\n` then ends the response normally (no ugly hangup); the frontend's SSE parser detects `event:error`, preserves already-rendered content, and shows an error bubble to the user.
- **AG-UI copilot:** the browser connects **directly** to platform's `/api/copilot/agui` via `@ag-ui/client` HttpAgent + CopilotKit's `agents__unsafe_dev_only` — POC posture, no Node bridge. Unlike `/api/chat*`, this endpoint **requires authentication** (`RequireAuthorization()` — no JWT, an invalid JWT, or a JWT missing a nonblank tenant/user claim → rejected/fail-closed); AG-UI session isolation is `{tenant}:{user}` from those JWT claims, never wire data. The frontend builds its `HttpAgent` inside the root component with `useMemo` keyed on `session.token`, sends `Authorization: Bearer`, and its custom fetch path must send a `401` through the same global logout that `apiFetch` uses. It now shares the same skill-routing/mem0/persistence core as `/api/chat*` (see the memory-layers entry below) — the copilot and ChatView are no longer functionally different brains, just different personas/transports. Frontend side: [frontend/AGENTS.md](frontend/AGENTS.md); platform side: [platform/AGENTS.md](platform/AGENTS.md).
- **Error shape:** every API returns ApiError `{timestamp, status, message, fieldErrors}` (camelCase). Response field naming is mixed **by design**: documents/workflows/analysis are snake_case (`chunk_count`, `required_role`, `created_at`); auth/config are camelCase (`updatedAt`). Do not "fix" either side.
- **Backend trust boundary:** backend (`:8002`) globally requires `X-Internal-Token: <INTERNAL_API_TOKEN>` on everything except `/health` (one middleware, `InternalTokenMiddleware`). Identity headers (`X-Tenant-Id`, `X-User-Id`, `X-User-Role`) are **not** gated by that same middleware — enforcement is per-endpoint: handlers that need tenant scoping call `RequireTenant()` themselves (missing `X-Tenant-Id` → `400`), while `X-User-Id`/`X-User-Role` stay optional by default (no header → empty/null) — except identity-requiring endpoints (D3/D7 runs, approvals, and config management) which call `RequireUserId()` or `RequireTenant()` as required (missing → `400`). `/api/config` (`GET` and `PUT`) are ADMIN-only and tenant-scoped: both require `[AdminOnly]` authorization filter (non-ADMIN → 403) and `RequireTenant()` identity check (missing `X-Tenant-Id` → 400); values are per-tenant (each tenant has its own isolated key–value store, shared defaults do not exist). Config values are ADMIN-authored content (e.g. `agent.defaults.system_prompt`), never USER-readable. Only platform and workflow call it; workflow (`:8001`) shares the same trust model. Both bind `127.0.0.1` and must never face LAN or public internet.
- **Async document processing:** platform publishes to RabbitMQ queue `documents.process` and returns `202 {id, title, status:"processing"}`; backend's consumer chunks/embeds/stores and flips status to `ready`/`failed`. The document is absent from `GET /api/documents` until consumed — eventual consistency by design (frontend bridges the gap with optimistic insert + polling). Broker unreachable at publish time → `502`.
- **Auth:** backend issues JWTs (HS256, shared `JWT_SECRET`), platform validates them. Frontend stores `{token, username, role, tenantCode}` in localStorage and sends `Authorization: Bearer`; ordinary API calls use `apiFetch`, while AG-UI uses `HttpAgent`'s custom fetch wrapper. Any `401` while logged in, including AG-UI, clears the session (and chat localStorage keys) and returns to login.
- **Two memory layers, don't confuse them:** *short-term* = Microsoft Agent Framework session store (`InMemoryChatHistoryProvider` + `SlidingWindowCompactionStrategy`, last 20 messages per session key, `minimumPreservedTurns:1`, turn-level atomic trimming so tool-call/tool-result pairs never get split), shared by both platform's hosted agents (AG-UI's `OperationsAssistant` and `ChatService`'s `ChatAssistant`); resets on restart. Isolation differs by chain: AG-UI uses `withIsolation:true` keyed on nonblank JWT `{tenant}:{user}` (fail-closed); `/api/chat*` uses `withIsolation:false` because its `conversationId` is already prefixed `{tenant}:{user}` at the derivation layer, deliberately preserving anonymous-chat continuity. AG-UI's resent full message arrays are deduped by ID with a conservative assistant role/content/tool-call fingerprint fallback for rebuilt assistant IDs. *long-term* = mem0 (cross-session facts), for authenticated users only: anonymous chat has short-term continuity but does **not** recall, remember, or persist. Best-effort is a shared pipeline boundary: every `IMem0Client` failure is logged and degrades (`recall` → empty, `remember` → no-op), including failures from replacement implementations. Everything else persists in appdb across restarts.
- **Skill concepts and engine boundary (P0–P5):** An **Agent Skill** is a portable Anthropic-style `SKILL.md` package (with optional `references/`, `assets/`, and `scripts/`), not a YAML flow. A **Business Workflow** is the declarative YAML node/sequence/branch/loop/script/tool flow compiled by the **Skill Engine** (`workflow/app/engine/`); `agent_skill_graph.py` is retained separately as the Agent Skill direct-invoke bridge graph factory and does not make Agent Skills Business Workflows. The physical `skill`/`skill_revision` tables retain both artifacts behind the trusted `kind` discriminator. A **Harness** is the fixed runtime LangGraph in `workflow/app/runtime/graph.py`; its D4 `workflow` Graph IR declaration is a **Harness Workflow** (governance/shape source, not a Business Workflow or executable graph). `engine/node_shell.py` is the per-node **Node Shell**: it enforces reads/writes, timing, trace, fatal short-circuit, and immutable-key protection; it is not the Harness. Platform's `WorkflowEngineClient` is the client for the whole Python engine (skills, Business Rules, nodes, and tools). During P2–P5, `/api/skills*` and `/api/business-workflows*` are deliberately dual-track for flow artifacts, while internal `POST /skills/{name}/invoke` stays unified across both kinds; `/business-workflows/validate` is the flow validation route and `/skills/validate` is its same-handler compatibility alias. P5/C8 do **not** remove that internal alias; alias retirement requires a separate consumer/usage/rollback gate. P5 may make the public `/api/skills*` Agent-Skill-only only after cleanup C8 proves Business Workflow traffic cutover, legacy flow-write usage `= 0`, and the rollback window has ended—never earlier. Deterministic chat routing remains kind-agnostic and never exposes native AG-UI tool events. **Skill invoke errors (422):** workflow returns a human summary plus snake_case field errors; platform maps them to camelCase `ApiError`.
- **Prompt manifest (P1):** Backend's internal-only `GET /api/prompt-manifests/{revision}/resolved` route returns raw pinned prompt composition (never proxied to browsers or UI tools); pinned runs embed `execution_snapshot.agent.prompt_manifest {revision, sha256}` (canonical hash immutable, omit entire key if no pin). Workflow's `_system_frame()` handles manifest-aware assembly; pinned-run manifest unavailability fails closed (`prompt_manifest_unavailable`). Platform composes five-slot prompt (tenant canary via backend's `GET /api/config/runtime/{key}` single-key allowlist for `prompt.manifest_revision`; fallback to constants on any failure; single resolution per-turn; transient errors skip cache, permanent errors with a revision cache negative for 60s). Both sides: `PROMPT_ARTIFACTS_ENABLED`/`PROMPT_ARTIFACTS_SHADOW` default false; shadow mode is observe-only (constants + warning, no pins accepted). Details: [plans/agent-architecture-improvements/03-prompt-model-runtime-plan.md](plans/agent-architecture-improvements/03-prompt-model-runtime-plan.md) plus the platform/workflow/backend area files.
- **Eval framework (E2):** Backend owns durable eval suite/revision/run/result authority (`eval_suite`, `eval_suite_revision`, `eval_run`, `eval_case_result`); platform proxies `GET eval-suites` (list/detail; the backend-only `revisions/{revision}` route is not proxied) and `GET/POST eval-runs*` under `/api/admin/operations`, which share D7's `AGENT_WRITE_TOOLS_ENABLED` pre-auth 404 gate — `RUN_EVAL_ENABLED` governs only the backend/workflow side. Workflow's `/evals/run` endpoint (internal, no `/api` prefix) executes a Backend-supplied versioned suite against a candidate deterministically; it returns per-case PASS/FAIL/ERROR verdicts and canonical identity, is stateless for eval, persists nothing, and is gated by `RUN_EVAL_ENABLED` (fail-closed 404). Backend's regression gate (`POST /api/admin/operations/regressions` with optional `eval_run_id`) recomputes `passed` from stored suite policy and case results server-side (never trusts the caller), enabling eval-driven release gates.
### Agent platform (D1–D7) — invariants only

Full contracts live in [docs/agent-platform-contracts.md](docs/agent-platform-contracts.md) — **read the relevant section there before changing any side of these**:

- **Agent Registry (D1):** `/api/agents*` is an ADMIN-only Builder API (platform → backend proxy) behind `AGENT_BUILDER_ENABLED` (default false, 404 fail-closed before auth). Never reuse it as a USER catalog. If-Match/ETag optimistic locking; ADMIN does not imply `workflow.manage`.
- **Business Rules (D2):** Agent `business_rules` is a canonical JSON AST (`version:1`), never code or prompt text. Workflow owns catalog/validator/three-valued evaluator; unknown facts resolve through explicit `onUnknown` (default deny), never silent false.
- **Direct Agent runtime (D3):** ADMIN-only test runs of immutable published snapshots behind fail-closed `AGENT_TEST_RUN_ENABLED`. Backend owns durable run/command/lease state; Workflow owns LangGraph execution + PostgreSQL checkpoints. No streaming, approvals, or write tools in this phase.
- **Workflow Designer & Orchestrator Registry (D4):** gated by `WORKFLOW_DESIGNER_ENABLED` + exact `workflow.manage` capability (ADMIN alone insufficient; disabled → 404 before auth). Workflow is the sole Graph IR compiler/validator; Backend owns drafts/revisions/ETags/locking; root context tools permit only `read`/`low` risk, all else fails closed.
- **Root Orchestrator runtime (D5):** `MULTI_AGENT_DISPATCH_ENABLED` fail-closed, default false. Backend owns immutable snapshots, command claim/renew/generation fencing, budgets, cascade cancel; Workflow claims only Backend-issued artifacts and enforces verifier independence, token caps, PASS-only aggregation. Public events are server-redacted.
- **Context Enrichment (E1/E3):** `CONTEXT_ENRICHMENT_ENABLED` is independently fail-closed but effective only with D5. Backend owns canonical, policy-evaluated context revisions, evidence, role views, task-local child context requests, and their transactional event history; Workflow may submit content only, never identity, ownership, task lineage, or role. E1/E3 routes are hidden with `404` while off (D5 context acquire keeps its existing not-ready contract). Read [docs/context-enrichment-contracts.md](docs/context-enrichment-contracts.md) before changing either side.
- **Agent Chat canary (D6):** Platform's `AGENT_CHAT_ENABLED` + `AGENT_CHAT_TENANT_ALLOWLIST` controls public canary selection. Backend's effective chat-runtime gate additionally requires D5; Workflow has no separate public chat-dispatch flag or endpoint. Ineligible callers stay on the legacy shared-core chat path; an explicitly requested unavailable Orchestrator fails closed, never falls back. Rollback is configuration-only.
- **Write tools & approvals (D7):** `AGENT_WRITE_TOOLS_ENABLED` fail-closed in all three services; only write tool is tenant-allowlisted `runtime.write_evidence`. Durable `waiting_approval` before any effect; once-only effect identity + atomic evidence/outbox make replay safe. `/api/admin/operations` requires exact `workflow.manage`.

## Coding Style

All development agents follow the constitution in [docs/coding-standards.md](docs/coding-standards.md): Karpathy's four principles, reuse-first, Node-First for `workflow/`, Business Rules live only in Backend, test value over test count, and **every plan must inventory old code that the new requirement turns into dead or duplicated code**. Semantic code search goes through the codebase-memory MCP; Grep is for literal strings.

Match the surrounding code's naming, structure, and idiom. Two deliberate choices you can't infer from a single file: both .NET test suites use **hand-written fakes, no mocking library**; the frontend has **no router and no UI library** by choice — do not add dependencies without explicit authorization.

## Commit & Pull Request Guidelines

Short imperative commit subjects. PRs: summary, test commands run, screenshots for UI changes, and call out any `infra/` configuration edits.

## Security & Configuration Tips

Do not commit secrets. Copy `infra/.env.example` to `infra/.env`; the real `OPENAI_API_KEY` lives only there, behind LiteLLM. All services talk to OpenAI-compatible models **through LiteLLM** (`http://localhost:4000`, env `LLM_BASE_URL`, virtual key `sk-1234`), never directly; provider/model routing belongs in `infra/litellm-config.yaml`. The chat model comes from env `CHAT_MODEL` (default `gpt-4o-mini`; override to `mock-gpt` to test without quota). Per-service env variables are listed in each area's AGENTS.md. Treat prompt/completion logging and Langfuse traces as sensitive in non-dev environments. `JWT_SECRET`, `INTERNAL_API_TOKEN`, and `POSTGRES_PASSWORD` have public dev defaults committed in the repo, identical across services (zero-config startup); before any non-loopback / non-dev deployment they must all be overridden — leaving the defaults is equivalent to running with publicly-known credentials for both authentication and the databases.

Line endings: all `*.sh` must stay LF — a CRLF shebang makes `./script.sh` fail with `not found` inside Linux build images; `.gitattributes` pins this.
