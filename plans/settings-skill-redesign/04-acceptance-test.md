# 驗收測試 — 系統設定重構 × 雙門 Skill 編輯器 × Configuration Set

> 狀態: **已交付能力的驗收記錄。** 依據: [01-plan.md](01-plan.md)、[02-spec.md](02-spec.md)、[03-design.md](03-design.md)；實際測試入口見 [plans README](../README.md)。
>
> P4 是跨 frontend/platform/backend/workflow 與 appdb 的**獨立重線**，不阻塞 P1–P3 的最小可用切片；P2/P3 的硬順序見「Phase exit criteria」。本文共 **58 案**，所有案例皆有唯一 ID、phase、前置條件、Given/When/Then、驗證層級與建議自動化位置。

## 1. 驗收原則與環境

- `Given / When / Then` 是可觀察契約，不以「有呼叫某 private method」代替使用者或服務可見結果。
- 邊界值同時驗 **on-point**（恰在邊界應接受）與 **off-point**（剛越界應拒絕）；拒絕須驗 HTTP status、`ApiError {timestamp,status,message,fieldErrors}` 與無副作用。
- .NET 使用 xUnit 與手寫 fake；資料庫唯一性、原子 activate、租戶查詢必須另有真 PostgreSQL fixture，不可只用 fake。
- workflow 使用 pytest；LLM 單元測試用 deterministic fake，但至少一條 compose→validate→store→invoke 真鏈不得 stub workflow validator/compiler/Harness。
- frontend 的純 patch 邏輯可用 Node assert；UI 以 lint/build 為最低門檻，關鍵 IA 與互動用瀏覽器 e2e。CodeMirror 必須驗 lazy chunk，不只驗 TypeScript 可編譯。
- 跨服務契約以 full-stack docker compose 執行，backend 只接受 internal token + identity headers；不得用直接呼叫 repository 取代代理鏈驗收。
- 測試租戶至少 `tenant-a`、`tenant-b`，各有 ADMIN 與 USER；固定時間/UUID 時須避免讓測試掩蓋 tenant cache key 或 revision 排序錯誤。

建議測試資料：custom skill `sales-rule`、builtin `kb_query`、五支骨架 `template_{retrieval,compare,stats,infer,inspire}`；Configuration Set `default-a`、`high-recall-a`、`default-b`。

## 9. Phase exit criteria 與硬順序

### P3 exit（必須早於三支 NL 骨架）

- `SSR-P3-001`～`006` 全綠；node 已註冊，Harness/trace/component version 可觀測。
- 才能合入含 `nl_logic` slot 的 `template_retrieval/infer/inspire`。若順序顛倒，`SSR-P2A-001` 必須在冷啟動即擋下。

### P1 exit

- `SSR-P1-001`～`009` 全綠；舊 workflow 頂層入口完全消失，Skill 功能樹、試跑、revision 與一般設定回歸均通過。

### P2a exit（與 deps mapping 同批）

- `SSR-P2A-001`～`006` 全綠。
- 五支 YAML 與 `_DEPS_BUILDERS` 擴充必須同一次提交；catalog 已可提供原始 `definition`。
- **硬順序：P3 → P2a(NL 三骨架)**；compare/stats 可較早驗，但 P2a 整體 exit 仍要求五支全綠。

### P2b/P2c exit

- compose 只有在 catalog definition 已上線後才能 exit；**硬順序：P2a catalog definition → P2b compose**。
- `SSR-P2B-001`～`011`、`SSR-P2C-001`～`002`、frontend lint/build 與 `SSR-X-001` 全綠。
- 最小可用切片為 P1+P2a+P2b+P3；P2c 可獨立延後，但不能宣稱 Python 線上編輯已交付。

### P4 exit（獨立重線）

- P4a backend → P4b platform/P4c workflow → P4d frontend 依依賴順序完成；`SSR-P4-001`～`019` 與 `SSR-X-002` 全綠。
- DB 原子性與唯一性須由真 PostgreSQL 驗；代理與 apply-at-execution 須由 full-stack 驗，不能只憑手寫 fake 宣告完成。
- P4 失敗不得阻塞已驗收的 P1–P3 MVP；但不得把「NodeParamsTab 佔位」算作 P4 完成。

### 全案 release gate

- `SSR-X-001`～`005` 全綠；frontend lint/build、workflow pytest、backend/platform xUnit 全綠。
- 任何跨租戶可見/可改、雙 active、template 可執行列表外洩、validator 被繞過、SSE 格式變更皆為 release blocker。

## 10. 明確非驗收範圍（YAGNI）

以下項目不應被寫成「缺陷」或阻擋本案 exit；若實作意外加入，仍須另做安全/相容性評估：

- 不退回 flow/logic/script 三欄位舊模型；不做視覺化拖拉流程編排。
- 簡單模式不揭露流程/node/state/YAML；不做組織自訂骨架 CRUD。
- 不 UI 化詞彙、口徑、意圖對照、公式規則；不促升 rerank 權重、變體數、容差、locator 權重。
- 不改公開聊天 API、chat SSE、AG-UI；回歸案例只保證它們不被破壞。
- 不建 `SYSTEM_ADMIN` 或全域預設管理表；只驗現行組織 ADMIN + tenant 隔離與程式內建全域 fallback。
- `nl_logic.output_key` v1 不支援動態 writes；只接受/保留 `business_result`。
- 不做匿名草稿 invoke；v1 僅「存後試」。
- `app_config` 不做 per-tenant；一般設定維持既有全域模型。
- 前端不新增 YAML parser；CodeMirror 僅用於 Python，既有 YAML textarea 不更換。
