# Backend Core Service (ASP.NET Core 10, `:8002`)

Area-specific guidance. Cross-service contracts (X-Internal-Token + identity headers, 202 flow, auth/JWT, ApiError) live in the repo-root [AGENTS.md](../AGENTS.md) — read that first when changing anything platform or workflow consumes.

## Layout

Solution `Backend.sln`, single project `src/Backend.Api` organized by feature folders — Auth, Conversations, Files, Retrieval, Analysis, Config, Skills, **Agents** — with no layered dependencies. Data access is Dapper 2.x + Npgsql 9.x directly against appdb (PostgreSQL with pgvector), no ORM; in lite mode can switch to in-memory repositories (singleton per-request snapshots, no persistence across restarts). `Common/ApiErrors.cs` is the centralized 404 message factory for consistency across endpoints. Tests in `tests/Backend.Api.Tests` (xUnit; all PostgreSQL-dependent tests run with tenant prefixing and IAsyncLifetime cleanup; hand-written fakes, in-memory fixtures).

## Commands (run from `backend/`)

```bash
dotnet build
dotnet test
dotnet run --project src/Backend.Api
```

Requires appdb running (default `DB_CONNECTION_STRING`: `Host=localhost;Port=5433;Username=postgres;Password=postgres;Database=springaitest`). DB tables and seeds are created idempotently on startup.

## Gotchas

- **Identity header enforcement** (`Common/IdentityHeaders.cs`): provides `RequireTenant()` and `RequireUserId()` helper methods. `RequireTenant()` ensures `X-Tenant-Id` header is present and non-empty (missing → `400`); `RequireUserId()` ensures `X-User-Id` header is present and non-empty (missing → `400`). Controllers should call these explicitly where the identity is required — never duplicate this logic in handler code.
- **appdb owns ALL persistent data** (users, tenants, conversations, documents, vectors, config, skills) — restarts do **not** clear history. Only platform's in-memory short-term window resets. **rag_chunks vector search:** `rag_chunks` table has an HNSW index on the embedding column (`rag_chunks_embedding_hnsw_idx` using `vector_cosine_ops`) for ANN; requires pgvector ≥ 0.5. **Chunk writes:** inserted as a single multi-line `INSERT ... VALUES (...), (...), ...` statement per batch (reprocessing is idempotent via DELETE-then-INSERT inside one transaction), avoiding N round-trips.
- **Agent Registry storage** (`Agents/` feature folder): five tables `agent` (draft definition; authoritative canonical UTF-8 bytes + SHA, with jsonb as query projection only; draft_version, draft_validated_version, published_revision, enabled soft-delete), `agent_revision` (immutable authoritative canonical bytes + SHA published per agent, status published/superseded), `agent_revision_skill` (join table, pins skill current_revision), `workflow` (runtime workflow registry), `workflow_revision` (published revisions). Legacy rows missing canonical bytes fail closed; draft/revision/run reads verify fixed-time SHA, strict no-BOM UTF-8, JSON shape, and canonical form before use. Draft mutation and validate use `If-Match` optimistic locking (409 stale, 428 missing). Publish revalidates and share-locks the tenant/system-visible enabled `agent-runtime` Workflow revision plus every enabled persisted Skill/current `skill_revision` in the same transaction before pinning; catalog-only/builtin Skills are not bindable in D1 because backend has no immutable artifact revision for them. Restore creates a new published revision. Soft-disable preserves management/audit visibility but runtime must separately require enabled+published. Set-like definition fields and nested JSON objects are canonicalized for stable hashes. Seed data: system `Default Agent-Runtime Workflow` fixed rev1 with explicit start/end; bootstrap structurally validates and reconciles this system fixture instead of preserving a known-bad old seed.
- **D4 Workflow/Orchestrator persistence** (`Workflows/`, `Orchestrators/`): Backend owns tenant-scoped drafts, ETags, immutable revisions, canonical bytes/SHA, reference locking, publish, and restore; Workflow remains the compiler authority and its current wire contract is exactly `d4-graph-ir-1`. Unknown or legacy compiler contracts fail closed. Orchestrator lifecycle revalidates context tools against Workflow `/tools` risk metadata (only `read`/`low`), locks all referenced revisions, and verifies the Verifier Agent's hash-protected canonical `runtime_workflow` reference matches its immutable projection. The referenced harness must be a tenant/system-visible published `agent-runtime` verifier graph with the supported compiler proof, governance shell, required stages, valid reachability, and no worker/write stages. Dapper and in-memory repositories must preserve the same preflight behavior.
- **Skills storage:** `skill` table (tenant_id, name, definition YAML, current_revision, `enabled`=soft-delete flag, `simple_form` jsonb NULL storing `{templateId, form}` for simple-mode UX state) + `skill_revision` audit table (one row per write, `definition_sha256`, never deleted) with atomic data-modifying CTEs on write. `DELETE` sets `enabled=false` (revisions retained for audit); re-`POST`ing a soft-deleted name revives it with a bumped revision (not a 409). `simple_form` is written on Create/Update only; Import/Restore operations leave it NULL; export does not include it (UI convenience field, not part of the portable skill definition). Custom skills are user-managed; built-ins live in workflow.
- **Skill validation at write time:** `PUT /api/skills/{name}` calls workflow's `POST /skills/validate` (`:8001`; workflow-internal routes have no `/api` prefix) as a request-time dependency — if workflow is unreachable, return `502`. This is deliberate: the engine is the only source of truth for syntax.
- **Skill export:** `GET /api/skills/{name}/export` returns a zip (`application/zip`, `filename="<name>.zip"`) in Claude Skill format. **flow** skills export a *single self-contained* `{name}/SKILL.md` — one top-level folder named exactly `name` (05 §0: `name` must equal the folder name, so unzipping yields a matching folder instead of a tool-chosen one), holding standard frontmatter `name`+`description` (description YAML-safe) + a body embedding the `definition` column verbatim inside one fenced ` ```yaml ` block (05 §3.1; byte-for-byte between the opening ` ```yaml ` line and closing ` ``` `; no `skill.yaml` entry). The workflow importer strips that single top-level folder and round-trips by extracting the first ` ```yaml ` block. **agentic** skills (and any flow skill imported with a stored package) export the stored package bytes verbatim (all entries, no re-assembly, no folder added) — the asymmetry is deliberate: byte-identical round-trip wins over re-layout. `SkillExporter` is pure string assembly + `System.IO.Compression`, no code execution; role is USER (same data as `GET /api/skills/{name}`, just zipped), tenant-filtered so cross-tenant is 404.
- **Document consumer** (`DocumentProcessor` BackgroundService): consumes RabbitMQ queue `documents.process` with prefetch 1 + manual ack; redelivery is idempotent (ON CONFLICT insert + skip-if-ready); chunk → embed → pgvector, then flips document status to `ready`/`failed`. Startup logs a retrying `BrokerUnreachableException` until the broker is up — expected noise, backed-off retry by design.
- **Embeddings:** `EMBEDDINGS_PROVIDER` is `fake` (deterministic, default — tests and E2E rely on it) or `openai` (routed through LiteLLM, needs `text-embedding-3-small` in `litellm-config.yaml`).
- **Seed data** (from `DbBootstrap`): tenants `demo-a`/`demo-b` (invite codes `demo-a-invite`/`demo-b-invite`); users `admin-a` (ADMIN, demo-a), `user-a` (USER, demo-a), `user-b` (USER, demo-b); password `password123`. In lite mode (`DB_PROVIDER=inmemory`), the same seed data is hardcoded into `InMemoryAuthRepository` with matching BCrypt hashes.
- **App configuration (app_config table):** tenant-scoped key–value store with composite primary key `(tenant_id, key)` (tenant_id text, key text). `ConfigController` calls `RequireTenant()` on both GET and PUT — missing `X-Tenant-Id` → 400; both are also `[AdminOnly]`, and since that is an authorization filter it runs first (non-ADMIN without a tenant header gets 403, not 400). Each tenant has an independent isolated store; there are no shared global defaults in the DB. `DbBootstrap` contains an idempotent migration that detects the pre-tenant schema (single `key PRIMARY KEY`) and atomically backfills existing rows: each old global row is CROSS JOINed to every tenant in the `tenants` table, then the schema is tightened to `NOT NULL tenant_id` and the composite key, all within a single advisory-locked transaction; if `tenants` is empty, old orphaned rows are deleted. Rolling back a backend deployment to a pre-tenant schema image will leak config across tenants (`SELECT * FROM app_config` returns all tenants' rows) and fail on INSERT (`NOT NULL` + composite key violation → 500). **Never roll back this migration.** Dapper and in-memory repositories both enforce tenant isolation; in-memory uses `(tenant, key)` tuple keys. No default rows are seeded for any tenant — new tenants start with an empty config, and frontend `AGENT_DEFAULT_CONFIG_FALLBACKS` provides programmatic defaults when values are unset.
- **InMemory repositories (lite-only, DB_PROVIDER=inmemory):** eleven singleton in-memory repositories live in `src/Backend.Api/Data/InMemory/` and are registered at startup: `InMemoryAgentRepository`, `InMemoryAgentRunApprovalRepository`, `InMemoryAgentRunRepository`, `InMemoryAuthRepository`, `InMemoryConfigRepository`, `InMemoryConfigurationSetRepository`, `InMemoryConversationRepository`, `InMemoryOrchestratorRepository`, `InMemoryRagRepository` (with true cosine similarity), `InMemorySkillRepository`, `InMemoryWorkflowRepository`. `DbBootstrap` is skipped entirely, and `AddNpgsqlDataSource` is not called. Tests reference the same fakes (now hosted in the main API project under a global using alias `Backend.Api.Data.InMemory`), ensuring behavior parity between test and lite mode.
- **Auth feature issues the JWTs** (HS256, optional repeated `capabilities` claims) that platform validates — `JWT_SECRET` must match platform's. Grants are persisted per user in `users.capabilities text[]` (default empty); role ADMIN does not imply `workflow.manage`. The demo `admin-a` user is explicitly granted it in both Dapper seed and in-memory seed. Claims are omitted when empty.
- **Agent Registry endpoints** are Builder management APIs: the entire `/api/agents*` controller requires `X-Internal-Token`, identity headers, tenant scoping, and ADMIN. There is deliberately no USER-readable draft endpoint; a future USER catalog must be a separate published-only, audience-filtered, redacted contract. Routes: `GET /api/agents` (management list), `POST /api/agents`, `GET /api/agents/{id}` (draft + ETag), `PUT /api/agents/{id}/draft` (If-Match), `POST /api/agents/{id}/validate` (If-Match mandatory), `POST /api/agents/{id}/publish`, `GET /api/agents/{id}/revisions`, `POST /api/agents/{id}/revisions/{rev}/restore`, `DELETE /api/agents/{id}`, `POST /api/agents/{id}/enable`. All responses snake_case.
- **D3 caller grants (contract v1):** persisted user capabilities use exact claims `tool.use:<toolName>` and `knowledge.read:<canonical-lowercase-document-UUID>`. Platform forwards nonblank signed claims in `X-User-Capabilities`; Backend intersects them with the immutable published Agent `allowed_tools` / `knowledge_sources`. ADMIN implies nothing, and malformed or wildcard claims fail closed. Scoped retrieval reuses `POST /api/retrieval/search` with both `scope_contract_version:1` and server-injected `knowledge_sources`; empty scope returns empty, and Dapper/in-memory enforce tenant plus exact document IDs. Omitting both scope fields is reserved for legacy non-Agent workflows.
- **D3 audience groups:** group membership is tenant-scoped in `user_group_membership`, signed as repeated canonical `groups` JWT claims, and forwarded internally as regenerated `X-User-Groups`. The whole set fails closed on malformed/over-bound input. Agent audiences use only `role:ADMIN`, `role:USER`, or `group:<canonical-id>`; only legacy bare `ADMIN`/`USER` are normalized/read compatibly. Old free-form bare group drafts must be edited explicitly to `group:<id>` before validate/publish.
- **D3 run recovery:** dispatch ACK and execution recovery are separate states. Expired unACKed dispatch claims are recoverable; an unACKed cancel is prioritized and may bypass an active execution lease. ACK/reclaim serialize on the run lock and recovery updates use command-state CAS. The latest ACKed start/resume remains durably recoverable after its queued/running execution lease becomes inactive; a lease-generation marker prevents the same crashed lease from reopening it repeatedly, while a 30-second no-lease grace covers a worker that ACKs and crashes before claiming its first lease. Entering `waiting_input` requires a nonblank durable `checkpoint_ref` and a strictly advanced `checkpoint_version`; resume rejects legacy/corrupt waiting rows without that identity. Resume commands pin the locked waiting-state `checkpoint_ref`; Workflow may replay the private resume input only for that exact durable interrupt identity, while a proven later same-thread checkpoint continues without reinjecting the old answer.
- **D5 Root/child runtime:** `orchestrator_run` stores strict canonical `RootExecutionSnapshot` bytes/hash plus server-owned `root_input {message, observed_at}`; caller context is never a recoverable root input. Root `start` commands are claimed by Workflow, not Platform. `dispatch/complete` is only an ACK; it retains the current fenced lease for `POST /api/orchestrator-runs/{run}/transitions`. Renew uses `/commands/{command}/lease/renew` with `{claim_token, lease_generation, lease_seconds}` and CAS-extends expiry without changing generation; stale/expired tokens fail. Child creation atomically persists ledger + immutable D3 `agent_run` + start command. The child snapshot has `execution_kind` `orchestrator-worker` or `orchestrator-verifier`, so Workflow must enforce the matching role. Child D3 terminal transitions mirror status/result and append `child_terminal` to the root in the same transaction; root cancellation cascades. `POST .../context/acquire` checks exact snapshot authority and returns `ready:false` with missing sources when no server-owned read-only adapter is available—never caller/model-invented context or provenance. `POST /api/admin/orchestrators/{id}/runs` rejects an oversized `message` (>16384 chars) with `413` (`message is too large`), matching D3 `AgentRunController.RequireMessage`'s status code for the same condition; an empty/blank `message` stays `400`.
- **D6 chat resolution:** `AGENT_CHAT_ENABLED` defaults false. Internal chat resolution uses the authenticated tenant/user and optional requested Orchestrator, returning either a pinned published Root snapshot or explicit `legacy`; it never trusts wire identity. Default routing requires an enabled tenant runtime binding and canary membership. Explicit unavailable or unauthorized selections fail closed. Chat-run allocation reuses D5 durability, idempotency, active-conversation uniqueness, commands, events, and immutable revision pins.
- **Context Enrichment (E1/E3):** `CONTEXT_ENRICHMENT_ENABLED` is effective only when D4 and `MULTI_AGENT_DISPATCH_ENABLED` are effective. When off, `/api/contexts`, `/api/context-views`, `/api/context-policies`, and child `context-requests` routes return `404`; D5 `context/acquire` retains its established fail-closed not-ready result. `context_revision`, evidence, views, active policy, and source catalogue are Backend-owned canonical records. Child requests and append-only deltas are task-local: derive the worker/verifier view from the immutable child kind, pin the selected source/adapter and evidence provenance, and never replace the root's latest ready revision. A delta writes its revision, request compare-and-swap version, delta record, and redacted root event in one transaction. See [context-enrichment-contracts.md](../docs/context-enrichment-contracts.md).
- **D7 approval/effect authority:** `AGENT_WRITE_TOOLS_ENABLED` defaults false. `agent_run_approval`, effect, execution-claim, evidence, and outbox persistence are Backend-owned. Workflow can create/consume/execute only internal approval resources under the run's exact tenant, action fingerprint, checkpoint and lease generation. Public `GET /api/runs/{run}/approvals` and idempotent approve/reject endpoints intentionally allow a qualifying authenticated business approver without `workflow.manage`; every decision rechecks tenant, required role, expiry, exact waiting state and separation of duties. The server-generated effect identity is consumed once, and evidence plus outbox are written atomically; replay or recovery therefore cannot create a duplicate effect. `/api/admin/operations` requires exact `workflow.manage`; failed regression evidence prevents a future-root rollout unless an idempotent audited override is present. Release controls retain immutable active snapshots and return aggregate/redacted observability only.
- **Never expose to LAN:** the service binds `127.0.0.1` only and *trusts* the `X-Tenant-Id`/`X-User-Id`/`X-User-Role` headers after `X-Internal-Token` passes. Its security model assumes only platform and workflow can reach it.
- **Env:** `DB_CONNECTION_STRING`, `INTERNAL_API_TOKEN` (default `internal-dev-token`), `JWT_SECRET`, `EMBEDDINGS_PROVIDER`, `RABBITMQ_URL`, `WORKFLOW_BASE_URL` (e.g. `http://localhost:8001`, used for skill validation at write time). **Lite-only:** `DB_PROVIDER` (unset or `dapper` = Npgsql + DbBootstrap, `inmemory` = eleven in-memory repositories with seed accounts, skips DbBootstrap and Npgsql connection pool).

## Testing

xUnit with hand-written fakes (no mocking library). Coverage spans Auth (registration, JWT signing), Retrieval (vector search), Config (ADMIN perms, tenant-scoped), chunking, fake-embedding determinism, and internal-token validation.
