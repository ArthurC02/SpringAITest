# Backend Core Service (ASP.NET Core 10, `:8002`)

Area-specific guidance. Cross-service contracts (X-Internal-Token + identity headers, 202 flow, auth/JWT, ApiError) live in the repo-root [AGENTS.md](../AGENTS.md) — read that first when changing anything platform or workflow consumes.

## Layout

Solution `Backend.sln`, single project `src/Backend.Api` organized by feature folders — Auth, Conversations, Files, Retrieval, Analysis, Config, Skills, **Agents** — with no layered dependencies. Data access is Dapper 2.x + Npgsql 9.x directly against appdb (PostgreSQL with pgvector), no ORM; in lite mode can switch to in-memory repositories (singleton per-request snapshots, no persistence across restarts). `Common/ApiErrors.cs` is the centralized 404 message factory for consistency across endpoints. Tests in `tests/Backend.Api.Tests` (xUnit; all PostgreSQL-dependent tests run with tenant prefixing and IAsyncLifetime cleanup; hand-written fakes, in-memory fixtures).

## Commands (run from `backend/`)

```bash
dotnet build
dotnet test
dotnet run --project src/Backend.Api
```

Requires appdb running (default `DB_CONNECTION_STRING`: `Host=localhost;Port=5433;Username=postgres;Password=postgres;Database=springaitest`). DB tables and seeds are created idempotently on startup.

## Gotchas

- **Identity header enforcement** (`Common/IdentityHeaders.cs`): provides `RequireTenant()` and `RequireUserId()` helper methods. `RequireTenant()` ensures `X-Tenant-Id` header is present and non-empty (missing → `400`); `RequireUserId()` ensures `X-User-Id` header is present and non-empty (missing → `400`). Controllers should call these explicitly where the identity is required — never duplicate this logic in handler code.
- **appdb owns ALL persistent data** (users, tenants, conversations, documents, vectors, config, skills) — restarts do **not** clear history. Only platform's in-memory short-term window resets. **rag_chunks vector search:** `rag_chunks` table has an HNSW index on the embedding column (`rag_chunks_embedding_hnsw_idx` using `vector_cosine_ops`) for ANN; requires pgvector ≥ 0.5. **Chunk writes:** inserted as a single multi-line `INSERT ... VALUES (...), (...), ...` statement per batch (reprocessing is idempotent via DELETE-then-INSERT inside one transaction), avoiding N round-trips.
- **Agent Registry storage** (`Agents/` feature folder): five tables `agent` (draft definition; authoritative canonical UTF-8 bytes + SHA, with jsonb as query projection only; draft_version, draft_validated_version, published_revision, enabled soft-delete), `agent_revision` (immutable authoritative canonical bytes + SHA published per agent, status published/superseded), `agent_revision_skill` (join table, pins skill current_revision), `workflow` (runtime workflow registry), `workflow_revision` (published revisions). Legacy rows missing canonical bytes fail closed; draft/revision/run reads verify fixed-time SHA, strict no-BOM UTF-8, JSON shape, and canonical form before use. Draft mutation and validate use `If-Match` optimistic locking (409 stale, 428 missing). Publish revalidates and share-locks the tenant/system-visible enabled `agent-runtime` Workflow revision plus every enabled persisted Skill/current `skill_revision` in the same transaction before pinning; catalog-only/builtin Skills are not bindable in D1 because backend has no immutable artifact revision for them. Restore creates a new published revision. Soft-disable preserves management/audit visibility but runtime must separately require enabled+published. Set-like definition fields and nested JSON objects are canonicalized for stable hashes. Seed data: system `Default Agent-Runtime Workflow` fixed rev1 with explicit start/end; bootstrap structurally validates and reconciles this system fixture instead of preserving a known-bad old seed.
- **D4 Workflow/Orchestrator persistence** (`Workflows/`, `Orchestrators/`): Backend owns tenant-scoped drafts, ETags, immutable revisions, canonical bytes/SHA, reference locking, publish, and restore; Workflow remains the compiler authority and its current wire contract is exactly `d4-graph-ir-1`. Unknown or legacy compiler contracts fail closed. Orchestrator lifecycle revalidates context tools against Workflow `/tools` risk metadata (only `read`/`low`), locks all referenced revisions, and verifies the Verifier Agent's hash-protected canonical `runtime_workflow` reference matches its immutable projection. The referenced harness must be a tenant/system-visible published `agent-runtime` verifier graph with the supported compiler proof, governance shell, required stages, valid reachability, and no worker/write stages. Dapper and in-memory repositories must preserve the same preflight behavior.
- **Artifact storage and dual-track contract:** `skill` and `skill_revision` remain the shared physical store; `kind` is the trusted discriminator, not an invitation to infer type from YAML. `kind='agentic'` is an **Agent Skill** portable `SKILL.md` package. `kind='flow'` is a **Business Workflow** declarative YAML artifact; its `simple_form` is UI-only. P2–P5 deliberately expose the same enabled flow row through both `/api/skills*` and `/api/business-workflows*`, using the same repository and revision sequence. Revisions/restore remain only on the Skill route because a historical row may mix kinds. Do not split tables or rewrite revision/run pins.
- **Business Workflow writes and export:** `/api/business-workflows*` owns flow CRUD/export and calls workflow's internal `POST /business-workflows/validate`; its 502-on-engine-unreachable behavior remains the syntax authority contract. Workflow's `POST /skills/validate` is a same-handler compatibility alias and is explicitly outside P5/C8 removal; its retirement needs a separate gate. During P2–P5, the old public flow create/update/export paths remain for compatibility. **P5 is not complete merely because the new routes exist:** only C8 evidence (new-route traffic cutover, old flow-write usage `= 0`, completed rollback window, and sign-off) authorizes `/api/skills*` flow writes to become `410`, removal of its flow-export fallback, and Agent-Skill-only list/detail visibility.
- **Document consumer** (`DocumentConsumerService` + `DocumentProcessor`): consumes RabbitMQ queue `documents.process` with prefetch 1 + manual ack; redelivery is idempotent (ON CONFLICT insert + skip-if-ready); chunk → embed → pgvector, then flips document status to `ready`/`failed`. Startup logs a retrying `BrokerUnreachableException` until the broker is up — expected noise, backed-off retry by design. **Failure semantics:** `DocumentProcessor.ProcessAsync` classifies each failure as transient (`DbException.IsTransient`, `HttpRequestException`, `TimeoutException`, `TaskCanceledException` — e.g. DB/embedding-provider blips) or terminal (everything else, e.g. payload/parse errors), returning a `DocumentProcessingOutcome` instead of swallowing exceptions; transient failures under `DocumentProcessor.MaxRetries` (3) do **not** mark the document failed and tell the consumer to retry, everything else (terminal, or transient past the retry cap) marks the document `failed` (best effort) and tells the consumer to give up. `DocumentConsumerService` never unconditionally ACKs a failure away: retryable outcomes are republished to the same queue with an incremented `x-retry-count` header (then the original delivery is ACKed — it's been replaced, not lost); terminal outcomes (plus unparseable/poison payloads and any unexpected exception) are manually copied to a sibling `documents.process.dlq` queue before ACKing. DLQ is a manually-published sibling queue rather than a native `x-dead-letter-exchange` queue argument on `documents.process` — that queue is a pre-existing durable queue (persists across restarts) declared identically (`arguments: null`) by platform's untouched publisher (`RabbitDocumentQueue`), and changing its declared arguments would throw `PRECONDITION_FAILED` against any already-existing instance.
- **Embeddings:** `EMBEDDINGS_PROVIDER` is `fake` (deterministic, default — tests and E2E rely on it) or `openai` (routed through LiteLLM, needs `text-embedding-3-small` in `litellm-config.yaml`).
- **Seed data** (from `DbBootstrap`): tenants `demo-a`/`demo-b` (invite codes `demo-a-invite`/`demo-b-invite`); users `admin-a` (ADMIN, demo-a), `user-a` (USER, demo-a), `user-b` (USER, demo-b); password `password123`. In lite mode (`DB_PROVIDER=inmemory`), the same seed data is hardcoded into `InMemoryAuthRepository` with matching BCrypt hashes.
- **App configuration (app_config table):** tenant-scoped key–value store with composite primary key `(tenant_id, key)` (tenant_id text, key text). `ConfigController` calls `RequireTenant()` on both GET and PUT — missing `X-Tenant-Id` → 400; both are also `[AdminOnly]`, and since that is an authorization filter it runs first (non-ADMIN without a tenant header gets 403, not 400). Each tenant has an independent isolated store; there are no shared global defaults in the DB. **Runtime single-key read:** `GET /api/config/runtime/{key}` is deliberately **not** `[AdminOnly]` (same execution-time posture as `ConfigurationSetController`'s `active` route and `PromptManifestResolutionController`'s resolved route) — it exists for server-to-server callers like platform's prompt manifest resolver, still `RequireTenant()`-gated, and restricted to a closed allowlist (`ConfigController.RuntimeReadableKeys`, currently only `prompt.manifest_revision`); any other key, or an allowlisted key with no stored value, is 404. `DbBootstrap` contains an idempotent migration that detects the pre-tenant schema (single `key PRIMARY KEY`) and atomically backfills existing rows: each old global row is CROSS JOINed to every tenant in the `tenants` table, then the schema is tightened to `NOT NULL tenant_id` and the composite key, all within a single advisory-locked transaction; if `tenants` is empty, old orphaned rows are deleted. Rolling back a backend deployment to a pre-tenant schema image will leak config across tenants (`SELECT * FROM app_config` returns all tenants' rows) and fail on INSERT (`NOT NULL` + composite key violation → 500). **Never roll back this migration.** Dapper and in-memory repositories both enforce tenant isolation; in-memory uses `(tenant, key)` tuple keys. No default rows are seeded for any tenant — new tenants start with an empty config, and frontend `AGENT_DEFAULT_CONFIG_FALLBACKS` provides programmatic defaults when values are unset.
- **InMemory repositories (lite-only, DB_PROVIDER=inmemory):** seventeen singleton in-memory repositories are registered at startup in `Program.cs`. Twelve live in `src/Backend.Api/Data/InMemory/`: `InMemoryAgentRepository`, `InMemoryAgentRunApprovalRepository`, `InMemoryAgentRunRepository`, `InMemoryAuthRepository`, `InMemoryConfigRepository`, `InMemoryConfigurationSetRepository`, `InMemoryContextRepository`, `InMemoryConversationRepository`, `InMemoryOrchestratorRepository`, `InMemoryRagRepository` (with true cosine similarity), `InMemorySkillRepository`, `InMemoryWorkflowRepository`. The other five are **not** under `Data/InMemory/` — each lives beside its interface in its own feature folder, a trap when grepping for "all in-memory repos": `InMemoryOrchestratorRunRepository` (`OrchestratorRuns/`), `InMemoryRuntimeBindingRepository` (`RuntimeDiscovery/`), `InMemoryEvalRepository` and `InMemoryOperationsGovernanceRepository` (both `OperationsGovernance/`), `InMemoryPromptArtifactRepository` (`PromptArtifacts/`). `DbBootstrap` is skipped entirely, and `AddNpgsqlDataSource` is not called. Tests reference the same fakes (now hosted in the main API project under a global using alias `Backend.Api.Data.InMemory`), ensuring behavior parity between test and lite mode.
- **Dapper ↔ InMemory parity is not automatic:** the two implementations are **deliberately independent**, so drift is invisible — lite/tests can be all-green while production behaves differently, or vice versa. When changing either side, diff the other side's: state-set filter conditions, ordering, tenant filtering, null vs. empty collection, ETag/version increment, atomicity/transaction scope, cascade integrity. Regression tests for this class of drift must assert **authoritative state** (the underlying real record), never a local mirror/cache field — a mirrored field can stay "correct" even while the underlying bug fires. Real cases: `CancelAsync`'s child-run cascade missed the `waiting_input` status; `Expire()` never cascaded to the underlying `agent_run` at all; D7 evidence writes were a two-lock check-then-act in InMemory versus a single `FOR UPDATE` transaction in Dapper. Partial-failure semantics must match Dapper's transaction semantics: Dapper's multi-statement transactions are all-or-nothing (failure rolls back, next attempt is a clean retry); if InMemory instead commits a terminal state after a partial failure, the early-exit guard on that state permanently skips retrying the record.
- **Auth feature is the sole JWT signer:** it loads one P-256 private PEM from `JWT_PRIVATE_KEY_PEM_BASE64`, signs ES256 with exact `JWT_ISSUER`, `JWT_AUDIENCE`, and `JWT_ACTIVE_KID`, and issues 24-hour tokens with optional repeated `capabilities` claims. Platform receives only the matching public-key ring. Rotate by publishing the new public key to platform first, then atomically switching backend's kid/private-key pair; retain the previous public key for more than 24 hours plus rollout margin. Grants are persisted per user in `users.capabilities text[]` (default empty); role ADMIN does not imply `workflow.manage`. The demo `admin-a` user is explicitly granted it in both Dapper seed and in-memory seed. Claims are omitted when empty.
- **Credential timing and input bounds:** login always performs one BCrypt verification; unknown users verify against a precomputed dummy hash before returning the same 401 as a wrong password. Login/register identity fields are bounded to 128 characters on both proxy and backend contracts, while platform rejects auth bodies above 16 KiB before forwarding.
- **Agent Registry endpoints** are Builder management APIs: the entire `/api/agents*` controller requires `X-Internal-Token`, identity headers, tenant scoping, and ADMIN. There is deliberately no USER-readable draft endpoint; a future USER catalog must be a separate published-only, audience-filtered, redacted contract. Routes: `GET /api/agents` (management list), `POST /api/agents`, `GET /api/agents/{id}` (draft + ETag), `PUT /api/agents/{id}/draft` (If-Match), `POST /api/agents/{id}/validate` (If-Match mandatory), `POST /api/agents/{id}/publish`, `GET /api/agents/{id}/revisions`, `POST /api/agents/{id}/revisions/{rev}/restore`, `DELETE /api/agents/{id}`, `POST /api/agents/{id}/enable`. All responses snake_case.
- **D3 caller grants (contract v1):** persisted user capabilities use exact claims `tool.use:<toolName>` and `knowledge.read:<canonical-lowercase-document-UUID>`. Platform forwards nonblank signed claims in `X-User-Capabilities`; Backend intersects them with the immutable published Agent `allowed_tools` / `knowledge_sources`. ADMIN implies nothing, and malformed or wildcard claims fail closed. Scoped retrieval reuses `POST /api/retrieval/search` with both `scope_contract_version:1` and server-injected `knowledge_sources`; empty scope returns empty, and Dapper/in-memory enforce tenant plus exact document IDs. Omitting both scope fields is reserved for legacy non-Agent workflows.
- **D3 audience groups:** group membership is tenant-scoped in `user_group_membership`, signed as repeated canonical `groups` JWT claims, and forwarded internally as regenerated `X-User-Groups`. The whole set fails closed on malformed/over-bound input. Agent audiences use only `role:ADMIN`, `role:USER`, or `group:<canonical-id>`; only legacy bare `ADMIN`/`USER` are normalized/read compatibly. Old free-form bare group drafts must be edited explicitly to `group:<id>` before validate/publish.
- **D3 run recovery:** dispatch ACK and execution recovery are separate states. Expired unACKed dispatch claims are recoverable; an unACKed cancel is prioritized and may bypass an active execution lease. ACK/reclaim serialize on the run lock and recovery updates use command-state CAS. The latest ACKed start/resume remains durably recoverable after its queued/running execution lease becomes inactive; a lease-generation marker prevents the same crashed lease from reopening it repeatedly, while a 30-second no-lease grace covers a worker that ACKs and crashes before claiming its first lease. Entering `waiting_input` requires a nonblank durable `checkpoint_ref` and a strictly advanced `checkpoint_version`; resume rejects legacy/corrupt waiting rows without that identity. Resume commands pin the locked waiting-state `checkpoint_ref`; Workflow may replay the private resume input only for that exact durable interrupt identity, while a proven later same-thread checkpoint continues without reinjecting the old answer.
- **D5 Root/child runtime:** `orchestrator_run` stores strict canonical `RootExecutionSnapshot` bytes/hash plus server-owned `root_input {message, observed_at}`; caller context is never a recoverable root input. Root `start` commands are claimed by Workflow, not Platform. `dispatch/complete` is only an ACK; it retains the current fenced lease for `POST /api/orchestrator-runs/{run}/transitions`. Renew uses `/commands/{command}/lease/renew` with `{claim_token, lease_generation, lease_seconds}` and CAS-extends expiry without changing generation; stale/expired tokens fail. Child creation atomically persists ledger + immutable D3 `agent_run` + start command. The child snapshot has `execution_kind` `orchestrator-worker` or `orchestrator-verifier`, so Workflow must enforce the matching role. Child D3 terminal transitions mirror status/result and append `child_terminal` to the root in the same transaction; root cancellation cascades. `POST .../context/acquire` checks exact snapshot authority and returns `ready:false` with missing sources when no server-owned read-only adapter is available—never caller/model-invented context or provenance. `POST /api/admin/orchestrators/{id}/runs` rejects an oversized `message` (>16384 chars) with `413` (`message is too large`), matching D3 `AgentRunController.RequireMessage`'s status code for the same condition; an empty/blank `message` stays `400`.
- **D6 chat resolution:** `AGENT_CHAT_ENABLED` defaults false. Internal chat resolution uses the authenticated tenant/user and optional requested Orchestrator, returning either a pinned published Root snapshot or explicit `legacy`; it never trusts wire identity. Default routing requires an enabled tenant runtime binding and canary membership. Explicit unavailable or unauthorized selections fail closed. Chat-run allocation reuses D5 durability, idempotency, active-conversation uniqueness, commands, events, and immutable revision pins.
- **Context Enrichment (E1/E3):** `CONTEXT_ENRICHMENT_ENABLED` is independently fail-closed but effective only with D5 (`MULTI_AGENT_DISPATCH_ENABLED`). When off, `/api/contexts`, `/api/context-views`, `/api/context-policies`, and child `context-requests` routes return `404`; D5 `context/acquire` retains its established fail-closed not-ready result. `context_revision`, evidence, views, active policy, and source catalogue are Backend-owned canonical records. Child requests and append-only deltas are task-local: derive the worker/verifier view from the immutable child kind, pin the selected source/adapter and evidence provenance, and never replace the root's latest ready revision. A delta writes its revision, request compare-and-swap version, delta record, and redacted root event in one transaction. See [context-enrichment-contracts.md](../docs/context-enrichment-contracts.md).
- **D7 approval/effect authority:** `AGENT_WRITE_TOOLS_ENABLED` defaults false. `agent_run_approval`, effect, execution-claim, evidence, and outbox persistence are Backend-owned. Workflow can create/consume/execute only internal approval resources under the run's exact tenant, action fingerprint, checkpoint and lease generation. Public `GET /api/runs/{run}/approvals` and idempotent approve/reject endpoints intentionally allow a qualifying authenticated business approver without `workflow.manage`; every decision rechecks tenant, required role, expiry, exact waiting state and separation of duties. The server-generated effect identity is consumed once, and evidence plus outbox are written atomically; replay or recovery therefore cannot create a duplicate effect. `/api/admin/operations` requires exact `workflow.manage`; failed regression evidence prevents a future-root rollout unless an idempotent audited override is present. Release controls retain immutable active snapshots and return aggregate/redacted observability only.
- **Operations governance extensions (E1/E2/E3/P1):** `RUN_EVIDENCE_ENABLED` (E1, default false) adds `operations_run_evidence`, an append-only companion to `operations_execution_metric` written by the same `POST /api/operations/telemetry` call whenever the nested `evidence` object is present and validates (validated *before* the legacy metric write, so a rejected envelope changes nothing at all); root/child lineage, `snapshot_sha256` and `prompt_manifest_sha256` are always resolved server-side from the run's own `agent_run`/`orchestrator_run_child`/`agent_revision` rows, never trusted from the caller. `GET /api/admin/operations/evidence-reconcile` proves the two ledgers never diverge. `RUN_EVAL_ENABLED` (E2/E3, default false) adds the durable eval suite/result authority `eval_suite`/`eval_suite_revision`/`eval_run`/`eval_case_result` (current-pointer + immutable-revision pattern, same as Skills), routes `GET /api/admin/operations/eval-suites*` and `GET/POST /api/admin/operations/eval-runs*` (idempotency is checked, and a replay/conflict resolved, *before* the runner call — never re-running Workflow just to discard the result); `POST /api/admin/operations/regressions` with an `eval_run_id` recomputes `passed` itself from stored suite policy/case results (fail-closed on an empty `required_case_ids` policy or any FAIL/ERROR verdict in the run, never the caller's boolean). `PROMPT_ARTIFACTS_ENABLED` (P1, default false) adds `prompt_component_revision`/`prompt_manifest_revision` (immutable, content-addressed by SHA, same idempotent-republish pattern), routes `/api/prompt-components*`/`/api/prompt-manifests*`; a published Agent revision may pin `prompt_manifest_revision`/`prompt_manifest_sha256`, `NULL` meaning published without a prompt manifest. `GET /api/prompt-manifests/{revision}/resolved` is the **sole** content-bearing route in the service — it resolves every component the manifest references to its raw text for Platform/Workflow's assemblers; it is gated by the same flag (404 while off) plus `RequireTenant()`, deliberately **not** ADMIN-gated like its sibling Builder routes (it is called at execution time, not authoring time), and must **never** be proxied by platform to a browser. When a published `agent_revision` carries a pin, `AgentRunSnapshotBuilder` embeds an optional `agent.prompt_manifest {revision, sha256}` in the D3/D5-child `execution_snapshot`; absent entirely when unpinned, so a pre-P1 snapshot stays byte-for-byte unchanged. The D5 root snapshot (`BuildOrchestratorRoot`) has no `agent` key at all and never carries this pin.
- **Never expose to LAN:** the service binds `127.0.0.1` only and *trusts* the `X-Tenant-Id`/`X-User-Id`/`X-User-Role` headers after `X-Internal-Token` passes. Its security model assumes only platform and workflow can reach it.
- **Credential startup gate:** outside `Development`, startup rejects blank or committed-development database, internal-token, RabbitMQ, issuer/audience, kid, or private-key values. Backend must never distribute its private key; only derived public PEMs belong in platform's verification ring.
- **Env:** `DB_CONNECTION_STRING`, `INTERNAL_API_TOKEN` (development default `internal-dev-token`), `JWT_ISSUER`, `JWT_AUDIENCE`, `JWT_ACTIVE_KID`, `JWT_PRIVATE_KEY_PEM_BASE64`, `EMBEDDINGS_PROVIDER`, `RABBITMQ_URL`, `WORKFLOW_BASE_URL` (e.g. `http://localhost:8001`, used for skill validation at write time), `RUN_EVIDENCE_ENABLED`, `RUN_EVAL_ENABLED`, `PROMPT_ARTIFACTS_ENABLED` (all default false, independently fail-closed). **Lite-only:** `DB_PROVIDER` (unset or `dapper` = Npgsql + DbBootstrap, `inmemory` = seventeen in-memory repositories with seed accounts, skips DbBootstrap and Npgsql connection pool — full list above).

## Testing

xUnit with hand-written fakes (no mocking library). Coverage spans Auth (registration, JWT signing), Retrieval (vector search), Config (ADMIN perms, tenant-scoped), chunking, fake-embedding determinism, and internal-token validation.
