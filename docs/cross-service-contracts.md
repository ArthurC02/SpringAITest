# Cross-Service Contracts

Invariants live in the repo-root [AGENTS.md](../AGENTS.md); this file holds the full contract details. Read the relevant section here **before changing any side of these contracts** — changing one side silently breaks the other.

## Public chat API (platform; P4-1 PARTIAL)

`POST /api/chat` (blocking), `POST /api/chat/stream` (SSE), `GET /api/chat/history`, and `GET /api/chat/history/page` all require JWT — `ChatController` carries a class-level `[Authorize]`, so a missing or invalid token is `401` on every one of them. Anonymous chat, anonymous history (the old empty-array response), and anonymous short-term continuity no longer exist. POST bodies take `message` plus optional `conversationId`; wire-level `userId` is removed. Missing or blank `conversationId` makes Platform generate a canonical UUID, and both POST endpoints return the effective value in `X-Conversation-Id`; `turnId` is not yet delivered. Identity, mem0 grouping, and persistence derive from JWT `{tenant}:{user}`. The AG-UI copilot shares authenticated persistence: its turns show up together with `/api/chat*` turns in chat history.

## Two SSE formats, both deliberate

`/api/chat/stream` writes hand-rolled `data:<value>` (no space); the AG-UI endpoint `/api/copilot/agui` writes protocol-standard `data: ` (with space). The frontend parses chat SSE with `fetch` + `ReadableStream` (`EventSource` cannot POST a body). Every proxy hop (Vite dev proxy, frontend nginx) must keep `proxy_buffering off` on SSE paths. **Streaming error frame:** if `/api/chat/stream` fails mid-transmission (after chunks have been sent), platform writes `event:error\ndata:<fixed Chinese message>\n\n` then ends the response normally (no ugly hangup); the frontend's SSE parser detects `event:error`, preserves already-rendered content, and shows an error bubble to the user.

## AG-UI copilot

The browser connects **directly** to platform's `/api/copilot/agui` via `@ag-ui/client` HttpAgent + CopilotKit's `agents__unsafe_dev_only` — POC posture, no Node bridge. Like `/api/chat*`, this endpoint **requires authentication** (`RequireAuthorization()` — no JWT, an invalid JWT, or a JWT missing a nonblank tenant/user claim → rejected/fail-closed); AG-UI session isolation is `{tenant}:{user}` from those JWT claims, never wire data. The frontend builds its `HttpAgent` inside the root component with `useMemo` keyed on `session.token`, sends `Authorization: Bearer`, and its custom fetch path must send a `401` through the same global logout that `apiFetch` uses. It now shares the same skill-routing/mem0/persistence core as `/api/chat*` (see the memory-layers section below) — the copilot and ChatView are no longer functionally different brains, just different personas/transports. Frontend side: [frontend/AGENTS.md](../frontend/AGENTS.md); platform side: [platform/AGENTS.md](../platform/AGENTS.md).

## Error shape & correlation

Every API returns ApiError `{timestamp, status, code, message, correlationId, fieldErrors}` (camelCase; `code` is stable machine-readable, with status→code mapping mirrored in platform/backend `ApiError.cs`). For 500 errors, the message is fixed and correlationId is generated (and also logged). **Correlation chain:** Platform is the authority and derives correlationId from its own `HttpContext.TraceIdentifier` (never trusts inbound values). It forwards via `X-Correlation-Id` request header to backend and workflow; backend validates (exactly one value, 1–128 chars, trimmed, no control chars) and overwrites its TraceIdentifier, then forwards to workflow the same way. Error responses (5xx, 4xx) include `X-Correlation-Id` response header (values = ApiError body's correlationId) so all three services' logs share one ID; success responses omit it. For 409 responses on paths with known versions, the latest ETag header is included. Response field naming is mixed **by design**: documents/workflows/analysis are snake_case (`chunk_count`, `required_role`, `created_at`); auth/config are camelCase (`updatedAt`). Do not "fix" either side.

## Auth

Backend is the sole JWT signer and holds one P-256 private key (`JWT_PRIVATE_KEY_PEM_BASE64`) selected by `JWT_ACTIVE_KID`; platform receives only the public verification ring (`JWT_PUBLIC_KEY_RING_JSON`). Tokens are ES256 and bind an exact `iss`, `aud`, and `kid`; platform does not try unrelated keys when `kid` is unknown. Key rotation is ordered: deploy a ring containing both public keys, atomically switch backend's active kid and matching private key, retain the old public key for **more than the 24-hour token lifetime** (plus rollout margin), then remove it. Keep issuer/audience stable during key-only rotation. Frontend stores `{token, username, role, tenantCode}` in localStorage and sends `Authorization: Bearer`; ordinary API calls use `apiFetch`, while AG-UI uses `HttpAgent`'s custom fetch wrapper. Any `401` while logged in, including AG-UI, clears the session (and chat localStorage keys) and returns to login.

## Two memory layers, don't confuse them

*Short-term* = Microsoft Agent Framework session store (`InMemoryChatHistoryProvider` + `SlidingWindowCompactionStrategy`, last 20 messages per session key, `minimumPreservedTurns:1`, turn-level atomic trimming so tool-call/tool-result pairs never get split), shared by both platform's hosted agents (AG-UI's `OperationsAssistant` and `ChatService`'s `ChatAssistant`); resets on restart. Isolation still differs by chain pending P4-3: AG-UI uses `withIsolation:true` keyed on nonblank JWT `{tenant}:{user}` (fail-closed), while `/api/chat*` still uses `withIsolation:false` with its canonical conversation UUID prefixed by authenticated `{tenant}:{user}` at the derivation layer. AG-UI's resent full message arrays are deduped by ID with a conservative assistant role/content/tool-call fingerprint fallback for rebuilt assistant IDs. *Long-term* = mem0 (cross-session facts), grouped by the JWT `{tenant}:{user}` and therefore covering every turn of both chains now that all chat transports require authentication. Best-effort is a shared pipeline boundary: every `IMem0Client` failure is logged and degrades (`recall` → empty, `remember` → no-op), including failures from replacement implementations. Everything else persists in appdb across restarts.

## Skill concepts and engine boundary (P0–P5)

An **Agent Skill** is a portable Anthropic-style `SKILL.md` package (with optional `references/`, `assets/`, and `scripts/`), not a YAML flow. A **Business Workflow** is the declarative YAML node/sequence/branch/loop/script/tool flow compiled by the **Skill Engine** (`workflow/app/engine/`); `agent_skill_graph.py` is retained separately as the Agent Skill direct-invoke bridge graph factory and does not make Agent Skills Business Workflows. The physical `skill`/`skill_revision` tables retain both artifacts behind the trusted `kind` discriminator. A **Harness** is the fixed runtime LangGraph in `workflow/app/runtime/graph.py`; its D4 `workflow` Graph IR declaration is a **Harness Workflow** (governance/shape source, not a Business Workflow or executable graph). Harness-internal Business Workflows may use registered nodes plus script/tool steps under Node Shell, budget, and effective-tool governance. Standalone flow invoke uses the lightweight preflight/budget/finalize wrapper in the unified `workflow/app/runtime/flow_harness.py` module; both paths emit `workflow_completed`. `engine/node_shell.py` is the per-node **Node Shell**: it enforces reads/writes, timing, trace, fatal short-circuit, and immutable-key protection; it is not the Harness. Platform's `WorkflowEngineClient` is the client for the whole Python engine (skills, Business Rules, nodes, and tools). During P2–P5, `/api/skills*` and `/api/business-workflows*` are deliberately dual-track for flow artifacts, while internal `POST /skills/{name}/invoke` stays unified across both kinds; `/business-workflows/validate` is the flow validation route and `/skills/validate` is its same-handler compatibility alias. P5/C8 do **not** remove that internal alias; alias retirement requires a separate consumer/usage/rollback gate. P5 may make the public `/api/skills*` Agent-Skill-only only after cleanup C8 proves Business Workflow traffic cutover, legacy flow-write usage `= 0`, and the rollback window has ended—never earlier. Deterministic chat routing remains kind-agnostic and never exposes native AG-UI tool events. **Skill invoke errors (422):** workflow returns a human summary plus snake_case field errors; platform maps them to camelCase `ApiError`.

## P3-R2 compatibility evidence

`artifact_compatibility_usage_total` uses only bounded dimensions and is emitted as a redacted JSON event for the versioned stdlib exporter. Platform replaces public invoke origin with a server-derived value, dependency validation hops do not count, and Workflow is the sole unified-invoke counting authority. Instrumentation/export code alone is not C8 evidence; production retention/extraction, observation, consumer attestation, rollback proof, and named approval remain required. ## Prompt manifest (P1)

Backend's internal-only `GET /api/prompt-manifests/{revision}/resolved` route returns raw pinned prompt composition (never proxied to browsers or UI tools); pinned runs embed `execution_snapshot.agent.prompt_manifest {revision, sha256}` (canonical hash immutable, omit entire key if no pin). Workflow's `_system_frame()` handles manifest-aware assembly; pinned-run manifest unavailability fails closed (`prompt_manifest_unavailable`). Platform composes five-slot prompt (tenant canary via backend's `GET /api/config/runtime/{key}` single-key allowlist for `prompt.manifest_revision`; fallback to constants on any failure; single resolution per-turn; transient errors skip cache, permanent errors with a revision cache negative for 60s). Both sides: `PROMPT_ARTIFACTS_ENABLED`/`PROMPT_ARTIFACTS_SHADOW` default false; shadow mode is observe-only (constants + warning, no pins accepted). Details: [plans/agent-architecture-improvements/03-prompt-model-runtime-plan.md](../plans/agent-architecture-improvements/03-prompt-model-runtime-plan.md) plus the platform/workflow/backend area files.

## Eval framework (E2)

Backend owns durable eval suite/revision/run/result authority (`eval_suite`, `eval_suite_revision`, `eval_run`, `eval_case_result`); platform proxies `GET eval-suites` (list/detail; the backend-only `revisions/{revision}` route is not proxied) and `GET/POST eval-runs*` under `/api/admin/operations`, which share D7's `AGENT_WRITE_TOOLS_ENABLED` pre-auth 404 gate — `RUN_EVAL_ENABLED` governs only the backend/workflow side. Workflow's `/evals/run` endpoint (internal, no `/api` prefix) executes a Backend-supplied versioned suite against a candidate deterministically; it returns per-case PASS/FAIL/ERROR verdicts and canonical identity, is stateless for eval, persists nothing, and is gated by `RUN_EVAL_ENABLED` (fail-closed 404). Backend's regression gate (`POST /api/admin/operations/regressions` with optional `eval_run_id`) recomputes `passed` from stored suite policy and case results server-side (never trusts the caller), enabling eval-driven release gates.

## Backend trust boundary

Backend (`:8002`) globally requires `X-Internal-Token: <INTERNAL_API_TOKEN>` on everything except `/health` (one middleware, `InternalTokenMiddleware`). Identity headers (`X-Tenant-Id`, `X-User-Id`, `X-User-Role`) are **not** gated by that same middleware — enforcement is per-endpoint: handlers that need tenant scoping call `RequireTenant()` themselves (missing `X-Tenant-Id` → `400`), while `X-User-Id`/`X-User-Role` stay optional by default (no header → empty/null) — except identity-requiring endpoints (D3/D7 runs, approvals, and config management) which call `RequireUserId()` or `RequireTenant()` as required (missing → `400`). `/api/config` (`GET` and `PUT`) are ADMIN-only and tenant-scoped: both require `[AdminOnly]` authorization filter (non-ADMIN → 403) and `RequireTenant()` identity check (missing `X-Tenant-Id` → 400); values are per-tenant (each tenant has its own isolated key–value store, shared defaults do not exist). Config values are ADMIN-authored content (e.g. `agent.defaults.system_prompt`), never USER-readable. Only platform and workflow call it; workflow (`:8001`) shares the same trust model. Both bind `127.0.0.1` and must never face LAN or public internet.

## Async document processing

Platform publishes to RabbitMQ queue `documents.process` and returns `202 {id, title, status:"processing"}`; backend's consumer chunks/embeds/stores and flips status to `ready`/`failed`. The document is absent from `GET /api/documents` until consumed — eventual consistency by design (frontend bridges the gap with optimistic insert + polling). Broker unreachable at publish time → `502`.

## O5 one-shot durable triggers

One-shot scheduled trigger execution: Backend holds trigger definitions (name, description, target Orchestrator ID + revision pin, sanitized input mapping, fire-at UTC timestamp, misfire window), fire ledger (occurrence stable identity, claim/lease, delivery status), and execution principal snapshot (tenant/user/role/groups/capabilities at trigger creation, not fire time). Platform proxies `/api/admin/triggers` (CRUD + `GET occurrences` fire history) and `/api/admin/triggers/{id}` under `AGENT_TRIGGERS_ENABLED` (default false; 404 fail-closed before auth) + `workflow.manage` authorization. Frontend provides sidebar entry "排程觸發" (list, create with CatalogPicker + datetime-local + input mapping, cancel, fire history) gated by `agentTriggersEnabled && canManageWorkflow`. Misfire: due occurrence not claimed within `misfire_window_seconds` is marked misfired and skipped (no backfill). Cancellation halts future fire but leaves existing/created runs intact. Fire uses immutable snapshot (principal, not current credentials) and calles Backend's existing D5 root-creation path; fails closed on principal disabled, target unpublished/disabled, revision mismatch, cross-tenant target, or flag off. At-most-once: identical occurrence reclaimed after restart returns the existing root run ID, not a duplicate. Workflow reads zero trigger state; trigger firings are indistinguishable from user-initiated runs. Composition: Backend `Triggers/` feature folder (tables `agent_trigger`, `agent_trigger_occurrence`), BackgroundService polling, durable repository parity (Dapper + InMemory), DTOs whitelisted (principal snapshot omitted in responses except summary; lease/fencing tokens never leaked). No recurring cron, webhook sources, external notifications, or in-place rescheduling (cancel + recreate instead, YAGNI). Test matrix: concurrent claims/restart idempotency/principal/target/revision/cross-tenant/misfire/cancellation/flag-off 404/DTO whitelist/D5 integration per [plan § 9](../plans/agent-architecture-improvements/04-operations-trigger-plan.md#9-验证-trigger-矩阵).

## Feature-gate 404s are indistinguishable from route-not-found

Whenever a flag is off, Platform and Backend answer with the same 404 body that service uses for any unknown route — never a "feature disabled" style message — so probing cannot tell a gated route from a nonexistent one. Do not reintroduce a gate-specific message or code.
