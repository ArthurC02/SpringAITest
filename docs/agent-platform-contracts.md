# Agent Platform Cross-Service Contracts (D1–D7)

Full detail for the agent-platform phases. The repo-root [AGENTS.md](../AGENTS.md) keeps only the one-line invariants; read the relevant section here **before changing any side of these contracts** — changing one side silently breaks the other.

## Agent Registry (D1, backend/platform split)

`/api/agents*` is an ADMIN-only Builder management API; platform transparently proxies it to backend and enforces `AGENT_BUILDER_ENABLED` (default false, all endpoints 404 fail-closed before auth when off). It contains full draft prompts/policies and must never be reused as a USER catalog; future discovery requires a separate published-only, audience-filtered, redacted DTO. Identity headers (`X-Tenant-Id`, `X-User-Id`, `X-User-Role`) + `X-Internal-Token` pass through; `X-User-Capabilities` is sent only when JWT `capabilities` is nonblank. Backend persists per-user grants and issues optional capability claims; ADMIN does not imply `workflow.manage`.

**ETag & optimistic locking:** draft update and validate use `If-Match` (missing → 428, stale → 409); publish rechecks and locks all Workflow/Skill references in one transaction. Skill catalog exposes Workflow-owned `bindable`: builtin/catalog-only Skills are visible but false until they have a backend immutable revision. Tool picker data comes from authenticated `GET /api/tools` and contains only safe name/kind/description/risk/returns metadata. Agents are soft-disabled, revisions audit-retained, and restore creates a new published revision.

## Business Rules (D2, all four services)

Agent `business_rules` is a canonical JSON AST (`version:1`), never Python/JavaScript or prompt text. Workflow owns the versioned fact/operator/action catalog, validator, pure three-valued evaluator and simulator at internal `/business-rules/*`; Backend persists only Workflow-returned canonical AST and revalidates validate/publish/restore fail-closed; Platform exposes ADMIN-only, `AGENT_BUILDER_ENABLED`-gated `/api/agents/catalog/rule-facts`, `/rule-actions`, `/api/agents/rules/validate`, and `/simulate`; Frontend renders catalog metadata but is not an execution authority. Missing, mistyped, unavailable-gate, or untrusted safety facts become `unknown` and resolve through explicit `onUnknown` (default deny), never silent false. D2 persisted Agent rules are gate-less v1 and lifecycle validation is fixed to `pre-action`; D3 runtime adapters must provide authenticated provenance-bearing facts before other policy gates become executable.

## Direct Agent runtime (D3, all four services)

ADMIN-only test runs execute an immutable published Agent snapshot behind the independent fail-closed `AGENT_TEST_RUN_ENABLED` flag ("independent" means each service gates it separately; at Platform the effective switch additionally requires `AGENT_BUILDER_ENABLED`). Backend owns durable run/command/event state, exact snapshot bytes and hashes, idempotency, optimistic command claims, execution leases, lease-generation fencing, deadlines, checkpoint lineage, audience/group checks, and the intersection of signed caller grants with the snapshot's tools/knowledge. Workflow owns LangGraph execution and PostgreSQL checkpoints; every lease generation gets a distinct thread identity, while resume is allowed only from the exact durable interrupt identity. `waiting_input` releases its lease, cancel is durable, expired claims/leases recover after restart, and event reads use a monotonic cursor. Runtime rules consume only server-authenticated provenance-bearing facts; scoped retrieval fails closed. Platform proxies accepted commands even when the best-effort Workflow kick fails, and Frontend persists one logical-attempt idempotency key across retries/reloads while exposing polling, resume, cancel, trace, and partial-output states. This phase deliberately excludes streaming, approval workflows, and write tools.

## Workflow Designer and Orchestrator Registry (D4, all four services)

Workflow owns the typed Node Catalog, canonical Graph IR compiler, validation, and write-safe simulation at internal `/workflow-designer/*`; Backend owns durable drafts, immutable revisions, ETags, reference locking, and canonical SHA verification. Platform exposes `/api/admin/workflows*` and `/api/admin/orchestrators*` only when `WORKFLOW_DESIGNER_ENABLED=true` and the JWT contains the exact `workflow.manage` capability (ADMIN alone is insufficient); the disabled flag returns 404 before auth. Frontend uses React Flow/ELK, keeps semantic Graph IR separate from `ui_metadata`, and is never the validation authority. Agent-runtime graphs declare `runtimeVariant` (`worker` or `verifier`); verifier Agents must pin a published read-only verifier harness, while Worker harnesses are rejected. Root context tools are resolved through Workflow's authenticated `/tools` risk metadata and permit only `read`/`low`; unknown, ambiguous, write, or privileged tools fail closed. The shared default worker fixture is `plans/agent-platform-redesign/fixtures/default-agent-runtime-workflow.json` and is checked byte-for-byte by Backend and compiled by Workflow tests.

## Root Orchestrator runtime (D5, Backend/Workflow/Platform/Frontend)

`MULTI_AGENT_DISPATCH_ENABLED` is independently fail-closed and defaults false. SYSTEM_ADMIN test-start is `POST /api/admin/orchestrators/{id}/runs` and requires exact `workflow.manage`; GET/events/cancel use authenticated owner/runtime authorization. Backend owns immutable root/child snapshots, canonical hashes, durable command claim/renew/generation fencing, exclusive event cursors, idempotent cancel, parent-child lineage, concurrency/child budgets, and cascade cancellation. Workflow claims only Backend-issued artifacts, validates the published Graph IR/runtime-adapter proof, performs bounded context acquisition, parallel Worker dispatch, independent read-only verification, repair, PASS-only aggregation, token reservations, result caps, and restart recovery. Every child pins Agent/Skill/runtime Workflow revisions, `execution_kind`, task envelope/provenance, and a hash-protected `orchestrator_token_cap`; Worker delegation and parallel writes are rejected. Public events are server-redacted; the frontend rebuilds cursor history and maps stable node IDs into the read-only Workflow Designer overlay.

## Agent Chat canary (D6, Backend/Workflow/Platform)

`AGENT_CHAT_ENABLED` is independently fail-closed in all three services; Platform additionally requires the exact tenant in `AGENT_CHAT_TENANT_ALLOWLIST`. For an authenticated eligible tenant, both `/api/chat*` and `/api/copilot/agui` resolve the tenant runtime binding, allocate/resume the same durable pinned Root Orchestrator path, best-effort dispatch through Workflow, and persist the assistant turn. Anonymous callers, non-allowlisted tenants, disabled flags, or a Backend `legacy` resolution stay on the existing shared-core chat path. A requested unavailable Orchestrator fails closed rather than falling back. Rollback is configuration-only: disable Platform `AGENT_CHAT_ENABLED` (or remove the tenant from its allowlist), then disable Workflow and Backend; durable D5/D6 records remain audit-retained.

## Write tools, approvals, and operations (D7, Backend/Workflow/Platform/Frontend)

`AGENT_WRITE_TOOLS_ENABLED` is independently fail-closed in all three services. The only shipped write tool is tenant-allowlisted `runtime.write_evidence`; no arbitrary tool is made writable by this flag. A write policy gate creates a durable `waiting_approval` record before any effect. An authenticated business approver uses `GET /api/runs/{runId}/approvals` and an idempotent `POST .../{approvalId}/approve|reject`; Backend rechecks tenant, required role, expiry, action fingerprint, exact waiting state/checkpoint, and separation of duties. Approval is not generic resume and does not require `workflow.manage`. On approval, Workflow consumes the once-only Backend effect identity; Backend atomically persists evidence plus its outbox record, so replay/retry cannot duplicate the effect. Internal execution claims and recovery are never public APIs. `workflow.manage` is required for the redacted `/api/admin/operations` release-control plane: record regression evidence, audited idempotent override, future-roots-only rollout, aggregate metrics/version comparison, and legacy inventory. A failed regression blocks rollout unless an audited override exists. Rollback changes only future runtime binding/revision; active runs retain pinned snapshots and records are audit-retained.
