# Infra (Docker Compose, project name `springaitest`)

Area-specific guidance for `infra/` (compose, LiteLLM, Langfuse, mem0) and the root `scripts/` startup helpers. Cross-service contracts live in the repo-root [AGENTS.md](../AGENTS.md).

## Run modes

- **Infra-only (default):** `.\scripts\start-infra.ps1` / `./scripts/start-infra.sh`. Starts everything **except** `frontend` and `platform` (they carry profile `full`): the infra tier (litellm, langfuse-web/worker, postgres, clickhouse, redis, minio, mem0) plus the always-on app tier (appdb, rabbitmq, backend, workflow). Host-run `dotnet run` platform + `npm run dev` frontend pair with this mode.
- **Full container mode:** `.\.scripts\start-full.ps1` / `./scripts/start-full.sh` / `docker compose --profile full up -d --build`. Adds the frontend and platform containers; platform publishes `:8080` to the host for localhost debugging. **Container internal traffic:** frontend nginx proxies `/api` to **compose service DNS `http://platform:8080`** (direct container-to-container, no host hop); the same nginx config serves both modes (dev-mode Vite uses host `:8080`, full-mode nginx uses service DNS).
- **Lite mode (no containers):** `.\scripts\start-lite.ps1` / `./scripts/start-lite.sh`. All four services (backend, workflow, platform, frontend) run on localhost; backend uses in-memory repositories (`DB_PROVIDER=inmemory`), platform uses in-memory mem0 (`MEM0_MODE=inmemory`), and observability is console-only (`OTEL_MODE=console`). LiteLLM still runs via `uvx` on `:4000`. No Docker or `infra/` containers required. Positioned for frontend development, fast iteration, and demos.
- Do **not** run host frontend/platform and `--profile full` simultaneously — both bind `:5173` and `:8080`. A stale host process can also shadow the container: check `Get-NetTCPConnection -LocalPort 8080` (or `lsof -i :8080` on macOS/Linux) before going full mode. Full run-mode matrix in [README.md](../README.md).
- **`docker compose --profile full up -d --build` can fail on `springaitest-mem0`:** on Compose v5.3, `--build` has been observed to still attempt a registry pull for the image-only mem0 service (it has `image:`, not `build:`) before falling back to the local image, and errors out with no matching remote tag. Workaround: `docker compose build backend workflow platform frontend` first (skips mem0), then `docker compose up -d --no-build`.
- **Prefer the start scripts over raw `docker compose up -d`:** they bring `postgres` up first and run `scripts/ensure-mem0-db.*` (creates the `mem0_app` DB and refreshes collation) so mem0 doesn't crash-loop waiting for its DB.

## Service gotchas

- **Service binding:** LiteLLM, mem0, Langfuse web/worker, RabbitMQ, and Postgres all bind to `127.0.0.1` only (loopback) — they hold secrets (LLM keys, user memories, user traces, broker credentials, app data) and must never face LAN or public internet. Only `platform` (`:8080`) and `frontend` (`:5173`) are optionally bound to the host interface (for development/demo); backend (`:8002`) and workflow (`:8001`) bind to loopback for internal-only access. In full mode, only frontend and platform join the isolated `frontend_platform_proxy` network (`TRUSTED_PROXY_CIDR`, default `10.253.254.0/28`); platform also joins `default` for downstream calls. Never attach other services to the proxy network or reuse the shared default CIDR as trusted forwarding scope.
- **LiteLLM (`:4000`):** all model/provider routing lives in `litellm-config.yaml`; virtual key `sk-1234`; `mock-gpt` is the keyless test model. mem0's embedder needs `text-embedding-3-small` registered here. Does **not** depend on langfuse-web — observability is best-effort, and Langfuse broker issues (clickhouse/redis/minio lag) must never stall the LLM or chat pipeline.
- **RabbitMQ (`:5672` loopback, UI `:15672`):** the `guest` account only allows loopback connections — inter-container traffic must use the `app` account (password env `RABBITMQ_PASSWORD`, default `app-dev-password`). Queue `documents.process` is durable — messages survive broker restarts. Healthcheck: `rabbitmq-diagnostics ping`. If `POST /api/documents` returns 502, check broker reachability and `RABBITMQ_URL` in both platform and backend.
- **Backend + Workflow cross-service:** backend's `WORKFLOW_BASE_URL` env (e.g. `http://workflow:8000` in compose, `http://localhost:8001` in host mode) is used at skill-write time to validate YAML against the engine. If workflow is unreachable, skill creation/update returns 502. Platform's `WORKFLOW_BASE_URL` env is used for skill invoke/validate/catalog endpoints and node catalog. Backend/workflow have compose healthchecks; workflow (and platform in full profile) waits for backend `service_healthy`, and backend waits for appdb `service_healthy` — no warm-up 502s.
- **Agent Builder flag:** the full-profile `platform` and isolated `platform-evidence` containers receive `AGENT_BUILDER_ENABLED` explicitly with a fail-closed default of `false`. Set it to `true` only when the ADMIN-only `/api/agents*` Builder API/UI should be exposed; `.env.example` documents the opt-in.
- **D3 direct-Agent runtime:** `AGENT_TEST_RUN_ENABLED` is independently fail-closed (`false`) in Platform and Workflow. Enabling it requires Workflow's `CHECKPOINT_DATABASE_URL` (container DNS: `postgresql://postgres:<password>@appdb:5432/springaitest`) and a nonblank `CHECKPOINT_HMAC_KEY`; Workflow deliberately refuses an in-memory fallback. The D3 verifier injects a per-run HMAC key into the isolated evidence profile.
- **D3 verifier:** `pwsh -File scripts/verify-agent-runtime-d3.ps1 [-Build]` starts only the needed evidence services on loopback `:8180`, drives deterministic `waiting_input`/resume, restart recovery, and cancellation, and retains no prompts, tokens, or HMACs. It does not remove volumes; it leaves the evidence profile running for inspection.
- **D4 Workflow Designer:** `WORKFLOW_DESIGNER_ENABLED` is independently fail-closed (`false`) in Platform and Backend. When enabled, management routes still require the exact signed `workflow.manage` capability; ADMIN alone is not sufficient. Keep the flag off in ordinary/evidence profiles unless the D4 authoring surface is under test.
- **D6 Agent Chat canary:** keep `AGENT_CHAT_ENABLED=false` by default in Platform, Backend, and Workflow. Platform also requires `AGENT_CHAT_TENANT_ALLOWLIST` (exact comma-separated tenant codes); enabling Backend/Workflow alone does not migrate traffic. Roll out one tenant only after its published runtime binding, Root Workflow, Worker, and independent read-only Verifier revisions are pinned. Roll back by disabling the Platform flag or removing the tenant first, then disable downstream flags; no database rollback or record deletion is required.
- **D5 multi-agent dispatch:** `MULTI_AGENT_DISPATCH_ENABLED` (Workflow) and `MULTI_AGENT_DISPATCH_ENABLED`/the corresponding Platform route gate must remain fail-closed outside D5 tests. Root execution is an internal Backend↔Workflow protocol over loopback: Platform allocates then best-effort kicks Workflow with a command ID; Workflow owns claim/renew/ACK/terminal transition and can recover expired commands. Enable only with Backend, Workflow, appdb, and the shared `INTERNAL_API_TOKEN` healthy; a failed kick is intentionally recoverable, not a reason to delete root data. Root context connectors are server-owned read-only adapters; absent adapters return explicit insufficiency rather than mock context.
- **mem0 (`:8000`) — the official `mem0-api-server` image ships broken**, wrapped by `mem0.Dockerfile`; known issues: (1) lacks libpq → Dockerfile adds `psycopg[binary,pool]`; (2) needs a `mem0_app` DB it won't self-create → start scripts create it; (3) latest image may die at startup on `ImportError: langchain_neo4j` — container shows Up but port 8000 never listens; chat is unaffected (mem0 is best-effort). The compose service uses the **prebuilt local image** `springaitest-mem0:latest` (`image:`, not `build:`) so `start-full`'s `--build` doesn't stall on it; rebuild manually with `docker build -f mem0.Dockerfile -t springaitest-mem0:latest .` (on amd64 hosts add `--platform=linux/arm64` if the upstream base lacks an amd64 manifest). Details in the mem0 section of [README.md](../README.md).
- **appdb (host `:5433`):** PostgreSQL with pgvector; all app data persists here across restarts. Volumes (8 total incl. Langfuse/postgres/appdb/rabbitmq data) must survive teardown — `docker compose down` **without** `-v`, never `volume rm`/`prune`. Healthcheck: `pg_isready`.
- **Frontend 502 from `/api`:** check platform reachability at `http://localhost:8080/actuator/health`. Infra-only mode expects host Vite; full mode requires `springaitest-frontend-1` running under the `full` profile.
- **Langfuse (`:3000`):** receives traces via two paths — LiteLLM `success_callback` (token/cost) and .NET OTLP. Treat traces as sensitive outside dev. Worker is separate (`langfuse-worker:3030` loopback).
- **Start scripts (`.ps1` and `.sh`):** both include `$LASTEXITCODE` checks (PowerShell) or `$?` checks (Bash) to fail fast if postgres/docker commands fail, preventing silent partial startup. Shared bootstrap logic (switch to infra, check `.env`, start postgres first, prepare mem0 database) has been extracted to `scripts/_bootstrap.ps1` and `scripts/_bootstrap.sh`, dot-sourced by `start-infra` and `start-full` scripts.
- **`.ps1` scripts need `pwsh` (PowerShell 7+), not Windows PowerShell 5.1:** `scripts/*.ps1` use the 3-argument `Join-Path $PSScriptRoot '..' 'infra'` form (the `-AdditionalChildPath` parameter), which only exists in PowerShell 6+. Running them under `powershell.exe` (5.1, still the Windows default) throws a parameter-binding error. Invoke as `pwsh -File scripts\start-infra.ps1` or from a `pwsh` prompt.
- **Shared-core black-box smoke companion:** run `pwsh -File scripts\verify-copilot-shared-core.ps1` against already-running services; it does not remove containers or volumes. `-Rebuild` starts/rebuilds full mode with `CHAT_MODEL=mock-gpt`; `-IncludeMem0Outage` runs the disruptive C-06 check and always restarts mem0 in `finally`. It is not sufficient release proof for C-01～C-08: it cannot inspect model inputs, session duplicate counts/tool-pair integrity, mem0 storage, or chunk timing; `mock-gpt` cannot validate routing. The canonical limits, parameters, and required additional evidence live in [README.md](../README.md#copilot-shared-core-black-box-smoke-驗證).
- **Release-evidence profile (currently release blocked/failed):** `docker compose -f docker-compose.yml -f docker-compose.evidence.yml --profile evidence up -d` adds loopback-only deterministic model (`:4010`), workflow capture proxy (`:8011`), and isolated `platform-evidence` (`:8180`). Prefer `pwsh -File scripts\verify-copilot-shared-core-evidence.ps1 -Lane Deterministic -StartEvidenceProfile`; add `-BuildEvidenceProfile` after evidence image/profile changes. Run the same wrapper with `-Lane RealModel -StartEvidenceProfile` for fixed-snapshot mem0/routing gates. It supplies a per-run HMAC key; capture endpoints retain only keyed-HMAC projections, never request bodies or identity headers. Latest deterministic evidence passes E-01/E-02/E-03/E-06, including complete content-event timing through nginx/Vite and run-scoped cleanup. Release remains blocked because E-04 failed to retrieve the authenticated mem0 fact and E-05's first final reply omitted the fixture number; that RealModel bundle did not preserve an auditable routing capture. See [release plan](../plans/copilot-shared-core/05-release-evidence-plan.md); bundles stay under ignored `artifacts/copilot-shared-core/`.

## Lite Mode Troubleshooting

- **LiteLLM uvx build failure:** `uvx --from "litellm[proxy]" litellm ...` pulls the latest litellm, which may require building wheels (Rust dependencies). On machines without Rust or MSVC build tools and no pre-built wheels, installation fails. Workaround: (a) install Visual Studio Build Tools (C++ workload), or (b) pin an older litellm version with pre-built wheels. This is an environment dependency issue, not a script bug.
- **dotnet run profile conflict:** if `dotnet run` ignores `ASPNETCORE_URLS=:8080` and binds to `:5008` instead, the launchSettings.json profile is taking precedence. Use `dotnet run --no-launch-profile --project ...` to bypass it.
- **npm subprocess on Windows:** `npm run dev` spawns child processes that must be reaped on script exit. Use `taskkill /T /F /PID <pid>` (kill tree) to avoid orphaned node processes holding `:5173`. On Linux/macOS, `kill -9 $pid` and recursive `pgrep -P $pid` kills are sufficient.
